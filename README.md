# Notification Service

Сервис уведомлений: приём через REST API, асинхронная доставка в каналы (email, telegram) с гарантией доставки и ретраями, отчёты по уведомлениям пользователя за период.

## Технологии

PHP 8.3 · Laravel 12 · PostgreSQL · RabbitMQ · Redis · Docker (compose) · Pest · PHPStan (larastan, level 6) · Pint · Sentry

## Запуск

Нужны только Docker и Docker Compose.

```bash
git clone git@github.com:vahagncrypto99-netizen/notification-service.git
cd notification-service
make setup
```

`make setup` сам создаст `.env`-файлы из примеров, соберёт образ, поднимет контейнеры (php-fpm, воркер очереди, планировщик, nginx, postgres, rabbitmq, redis), установит зависимости, сгенерирует ключ и накатит миграции.

Дальше:

- API — `http://localhost/api/...`; аутентификация s2s: `Authorization: Bearer <token>` + HMAC-подпись канонического запроса (`X-Timestamp`, `X-Signature = hmac_sha256(secret, METHOD \n URI \n TIMESTAMP \n BODY)`), пары `token:secret` — в `API_AUTH_CLIENTS` (`main/.env`)
- Health — `http://localhost/api/health` (БД, брокер, кэш; без подписи)
- Swagger UI — `http://localhost/api/documentation` (OpenAPI 3, PHP-атрибуты swagger-php; перегенерация — `make docs`)
- Проверки качества — `make check` (тесты + PHPStan + Pint)
- Логи — `make logs`; RabbitMQ UI — `http://localhost:15672` (креды в корневом `.env`)

## Архитектурные решения (кратко — что и почему)

- **Домен и доставка разделены.** `app/Base/Notification` — бизнес (статусная машина, ретраи, отчёты, события); `app/Services/Delivery` — физическая доставка (очереди каналов с приоритетом/отложкой, фабрика именованных сендеров, крон-отправка, троттлинг Telegram). Домен знает только `ChannelSenderInterface` — новый канал или провайдер добавляется конфигом и классом, без правок существующего кода.
- **Гарантия доставки — БД как источник истины, а не брокер.** Уведомление создаётся в `processing`, доставляется джобой с 5 ретраями (экспоненциальный backoff), терминальный сбой фиксируется в `failed`. Потерянные джобы (упавший брокер, убитый воркер) добирает watchdog-крон, гонка «watchdog против живой джобы» закрыта условными UPDATE-переходами статусов.
- **RabbitMQ, а не Redis/Kafka.** Durable-очереди, ack после обработки, DLX-ретраи — семантика именно очереди задач; Kafka — лог событий (нет per-message retry), Redis-очереди — durability уровня кэша. Redis оставлен для кэша и счётчиков rate limiting.
- **Единый контракт API** `{success, message, payload}` на все ответы, включая валидацию, 401/429 и 500. Контроллеры тонкие (DTO → Manager → ApiResponse); менеджер оборачивает операции в try/catch: доменные отказы несут HTTP-код, неожиданные сбои — лог + Sentry.
- **Валидация — в Spatie-DTO (`validateAndCreate`), а не FormRequest.** Осознанное отступление от буквы ТЗ: требование «валидировать вход до бизнес-логики» выполнено полностью, но правила объявлены рядом со структурой данных — DTO невозможно создать в обход валидации, и по слоям передаётся типизированный объект.
- **Отчёты устойчивы к падению на середине**: генерация во временный файл с атомарным rename, статус `done` — только после переноса; агрегация — один SQL по покрывающему индексу `(user_id, created_at) INCLUDE (channel, status)` (index-only scan: 0.7 ms против 8 ms на 300k строк).
- **Доменные события наружу** (`notification.sent` / `notification.failed`) публикуются версионированным конвертом в fanout-exchange RabbitMQ — будущие подписчики (аналитика, аудит) не требуют правок сервиса.
- **Инфраструктура**: один процесс — один контейнер (без supervisor), минимальный alpine-образ (~99 MB), порты только на 127.0.0.1, `no-new-privileges`, non-root, healthcheck и ротация логов у каждого сервиса, отдельная тестовая БД.

## Что бы я улучшил в продакшне

Не «добавить всё лучшее», а следующие шаги — каждый закрывает конкретный известный предел текущей реализации:

**1. Реальные провайдеры каналов.** Каркас готов (фабрика сендеров, карта мессенджеров) — остаётся вернуть сетевые клиенты: Telegram Bot API через Guzzle, ESP для писем (Unisender/SES) вторым named-сендером с канареечным переключением через `NOTIFICATIONS_MAIL_SENDER`. Токены — в секрет-менеджер, не в env. Критично: **идемпотентный ключ** в запросах к провайдерам — ack-потеря у брокера означает редкую повторную доставку джобы, и без ключа пользователь получит дубль сообщения.

**2. Получатели и deliverability.** Сейчас адреса — заглушки от `user_id`; в проде — profile-сервис (email/chat_id) с кэшем. Для почты — suppression-механика: обработка bounce/complaint-вебхуков провайдера, отписки с `List-Unsubscribe`, отсев временных email-доменов (точка расширения уже есть в `Delivery\Mail\Sender`). Без этого деградирует репутация отправителя — главная реальная боль почтового канала.

**3. Строгий transactional outbox.** `dispatch`-после-записи + watchdog закрывают потерю джоб с латентностью до порога watchdog'а (минуты). Если SLA жёстче — outbox-таблица в одной транзакции с бизнес-записью + релей, и publisher confirms у RabbitMQ. То же для событий в fanout-exchange: сейчас сбой их публикации только репортится в Sentry.

**4. Эволюция аутентификации.** Статические HMAC-пары адекватны для единиц внутренних потребителей; при росте числа клиентов или self-service — OAuth2 client credentials / mTLS через gateway или service mesh, ротация секретов по расписанию. Счётчики rate limiting уже в Redis — горизонтальное масштабирование fpm их не ломает.

**5. Наблюдаемость сверх Sentry.** Метрики в Prometheus: глубина очередей (у RabbitMQ готовый prometheus-плагин), доля `failed`, p95 «создано → отправлено», размер очередей каналов. Алёрт на рост зависших `processing` — ранний сигнал деградации доставки, сейчас он виден только в логах watchdog'а. Логи уже в stdout/stderr — подключение Loki/ELK это замена лог-драйвера compose, ноль правок кода.

**6. Данные под рост.** `notifications` — append-only таблица с горячим хвостом: партиционирование по `created_at` + retention (архив в S3); файлы отчётов — в объектное хранилище с подписанными ссылками и TTL вместо локального диска.

**7. Масштабирование воркеров.** Сейчас один воркер слушает обе очереди; в проде — отдельные деплойменты на очередь (доставка ≠ отчёты) с автоскейлом от глубины очереди и DLQ с разбором причин вместо только терминального статуса в БД.

**8. CI/CD.** Пайплайн собирается из существующего `make check` (тесты + PHPStan + Pint) + сборка образа + миграции в деплой-джобе — всё уже в контейнерах.
